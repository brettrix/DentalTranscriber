# Decisions

Choices made where BUILD_PROMPT v4.3 was unclear. Each keeps the invariants in section 1.1.

## Sources and transcription
- **Text-mode format.** Lines start with a role prefix in any case (`DENTIST:`, `Dentist:`). One speaker id per role, in order of first appearance (S0, S1, …). An optional explicit id (`DENTIST [S2]:`) allows two ids for one role. Unprefixed lines continue the previous utterance. Utterance ids are `u1…un`; timestamps are null.
- **Text-mode provider response** is stored byte for byte as `sources/provider_response.txt` (the typed transcript is the provider response). Deepgram responses are stored as `sources/provider_response.json`.
- **Audio roles** start as an unconfirmed overlay (`Other`, `set_by: unconfirmed`); Stage B refuses to run until a human confirms them.

## Entities and hashes
- **Relationship kind field** is named `relation_kind`, because `kind` is the entity discriminator (`problem | relationship | item`).
- **Symptom severity** is stored as `symptom.score` (a number with a required `spoken_number` derivation), with the patient's words in `value`, because 7.2 requires a deterministic derivation for severity scores.
- **Finding** has an extra `observation` attribute (the "test or observation" in 6.3) alongside `test`.
- **Allergy** has an `original_wording` attribute, so a substance that isn't in the drug table (e.g. latex) keeps its wording with a null normalized `substance` (7.2).
- **BP derivations.** A `bp_reading` derivation is written per attribute (`attributes.systolic` and `attributes.diastolic`, same `from` text); Cv recomputes the reading and compares the matching component.
- **`speaker_ids` and `roles`** are filled by the Linker from the cited utterances and the role overlay. Agents never set them.
- **`content_hash`** covers the clinical content fields, including `problem_id` and `assertion_source`. Derivations are in `support_hash` with the evidence.
- **Versions.** A matched entity gets a new version when either hash changes (not only `content_hash`), so every check execution and disposition binds to a distinct version.
- **Critical types.** All problems and relationships are treated as critical (a relationship can suppress a target rule, so it is treated conservatively), as is any item that names a tooth.
- **Tooth-target items in the 6.4 example.** The example's `test: "cold"` has no derivation; `test` is a semantic attribute and needs none. The example passes as written.

## Checks
- **Negation scope.** An `absent`/`denied` entity needs a derivation with `rule: "negation"` naming the cue (`from`) and the `concept`. Cue and concept must be in the same span, with one exception: a clinician's question and the patient's direct answer ("Any pain when you bite down?" / "Not really."), when both utterances are cited, adjacent, and the first ends with "?". Without this, ordinary Q&A negatives could never pass Cv.
- **`unconfirmed` is terminal** for `checks_finished` (section 12), but an unconfirmed entity is never accepted (9.0).
- **Agent quotes, not offsets.** Agents return quotes; the Linker finds offsets by exact search, falling back to rapidfuzz only to point Cv at the nearest text. Span text keeps the agent's quote, so a non-exact quote fails Cv and goes to repair.

## Models
- Producers and checkers use `claude-sonnet-5-5` (spec). Forced `tool_choice` is rejected on Sonnet 5.5, so calls use `tool_choice: auto` with a prompt instruction, and a missing or invalid tool call gets the one schema re-ask (10). Thinking is adaptive (default on Sonnet 5.5); per-agent effort is set in `config/agents.yaml`.
- Server-side refusal fallback (`fallbacks: "default"`) is enabled on every call; the trace records the model that actually answered.
- The eval-only Grader uses `claude-opus-5-5` with a 180 s timeout, so grading isn't done by the same model as the producers.

## Pipeline mechanics (stages 2–3)
- **Graph versions per run.** A run commits a version after the Linker, after Stage C, and at freeze (Stage D). Human actions each add one version. A stage-E failure task is a graph change, so it adds a version too.
- **Staging before graph.** When nothing can commit (no chief problem), stage-failure tasks are kept in `staging.json` until a graph exists.
- **Registry text for B1–B4** comes from Br's output, keyed `P1`, `P2`, …; the Linker resolves those keys and the agents' own local keys within one batch, in any order.
- **Repair** gets the entity in agent form (quotes instead of offsets) and returns revised items with the same `id`; a revision that changes nothing is ignored. Registry (problem/relationship) issues are never sent to repair: they become high-severity `registry_issue` tasks. This also applies to B0's problems.
- **R2 omission routing.** R2 suggests the item type its subject belongs to, so an uncovered contradiction goes to the right team extractor's repair call.
- **Unknown option links** create a low-severity task (6.8) as well as the `unknown_option_link` flag.

## Cs comparison calibration (stage 3, from case 1)
- **Inputs.** Cs is told the entity type it is checking and sees the producer's evidence quotes as "focus quotes" inside a ±2-utterance window. It never sees the producer's values. Without the type and focus it can't tell which assertion in a window to extract.
- **`absent` vs `denied`** count as the same negated assertion. The guide says when to use each, but which one is right depends on who speaks, and that is already compared through `assertion_source`.
- **Non-critical free text** (e.g. a finding's `observation`, `result_description`, `intensity`, the item's `target.free_text`) is compared as one combined description through Ce. Critical free text (diagnosis, option, procedure, referral destination) is compared attribute by attribute. On case 1, field-by-field comparison failed entities only because the same words were filed under a neighbouring field.
- **The checker adding a non-critical detail** the producer left null is not a mismatch. Any difference on a critical attribute is.
- **Ce** is asked whether the checker's reading supports the recorded value: wording and hedges ("about" vs "maybe") are equivalent; a changed or dropped clinical qualifier is not.
- **Cs extra assertions** count as omissions only if no entity cites that utterance at all. Co does the fine-grained, entity-aware omission check.
- Case 1 team run, before → after calibration: semantic pass 12/23 → 22/23 (same transcript); the remaining failure was a real ambiguity (a negative percussion test recorded as `absent`), now addressed in the extraction guide.

## E2 / E3
- **Quadrants for coarse locations.** Complaint locations such as "upper left" are compared with a tooth by Universal quadrant (glossary `QUADRANT_PHRASES`); a location with neither a tooth nor a recognizable quadrant gives `target_not_assessable` (low).
- **Allergen classes** (e.g. penicillin → amoxicillin, ampicillin) live in `rules/drug_allergy.json`, together with the glossary's brand/generic and combination-ingredient tables.
- **E3 questions are flags** with `origin: E3`, `question: true`, low severity, scored separately from E2 flags in the evaluation. Python finds the runnable rule instances (mode plus preconditions); the agent only words the question and cites entity ids from the instance's list.
- **E3 results are cached** by an inputs hash over the cited entities' hashes and the rule file, so human edits that don't touch those entities don't re-call the model. A failed E3 is not re-run while its inputs are unchanged unless the dentist presses Retry. An E3 failure task does not block approval (10.1: the dentist *may* accept it).

## Human correction and approval (stage 5)
- **An edit** creates a new human-entry version (owner `human`, `human_entry` evidence naming the reviewer and reason) that supersedes the old version, so source-backed checks are `not_applicable` on it. A Dentist edit of critical content also records `dentist_confirmed`.
- **Re-checks after human edits.** Every human change re-runs Cv (and Cs in team mode) for any source-backed entity whose current hashes have no matching execution, so a committed graph never holds a `not_run` summary. A team-mode problem/relationship edit re-runs Cs on every problem-scoped entity, as required.
- **No graph yet (Br or B0 failed).** The registry is entered through `enter_registry`. By the Dentist it takes effect and extraction re-runs (Br is recorded `not_applicable` while a human registry exists; an extractor's own chief problem resolves to the human one). By an Assistant it waits in `pending_registry.json` for the Dentist (critical-change policy).
- **Staged records and approval.** Only staged records from the latest run block approval. Older staged records stay in `staging.json` unchanged for audit.
- **Reruns.** Human-entered entities carry over unchanged. Their `human_entered` disposition is re-recorded if the bound hashes moved (e.g. a role change for a cited speaker), but `dentist_confirmed` carries only while it still binds. A regenerated entity that a human removed or edited is committed as superseded inside the same Linker transaction, so whole-graph validation sees one chief problem.
- **Conflicts between a human entry and a regenerated entity** are raised only for single-valued subjects (not findings, symptoms, instructions or consent elements, which legitimately share a type and tooth).
- **Approval-matrix rows** are checked from the graph itself (failed checks, conflicts, tasks, staged records, sections, pending changes); the flag rows cover the remaining high and safety-critical flags. "Marked for dentist" is a flag action. An E3 failure task does not block dentist approval (10.1 says the dentist *may* accept it).
- **Dismissing a safety-critical flag** is Dentist-only. A dismissal is stored in the flag's history (keyed by its inputs hash) and never changes a check result.

## Deepgram (stage 6)
- Parameters were checked against Deepgram's current docs: `model=nova-3-medical` (a listed value); `keyterm` repeated once per term (the glossary's 56 terms are far below the 500-token keyterm cap); `utterances`, `smart_format` and `punctuate` set to `true`. `diarize=true` is kept because it is still accepted, though the docs now mark it deprecated in favour of `diarize_model`. Switch to `diarize_model` if Deepgram removes it.
- Audio sessions start with an unconfirmed role overlay; `run_pipeline` refuses Stage B until a human confirms roles on the Role confirmation tab.

## Evaluation (stage 7)
- **Gold.** Development and matrix gold are drafted by Claude (`annotated_by: claude`, `checked_by: null`) from the scripts and answer keys. Every report says the numbers are provisional until a person checks the gold. Where the answer key is ambiguous (e.g. "looks like a cracked tooth" as definite vs possible), the gold entry has a `note`.
- **Matrix.** 17 cases from the section 14.1 table plus `m18_two_problems`, which the "finding moved to the wrong problem" fault needs. Each matrix case has a quick-note BP (except `m16_no_bp`), so `bp_reading` doesn't fire everywhere. Each case's `expect.json` turns the table's expectation into machine checks, and lists flags the annotation accepts as legitimate (`tolerated`). These are reported separately, never silently dropped.
- **Matching.** Entities need the same kind and type, the mapped problem (encounter items aside), and at least one shared utterance or quick-note id. Pairs are chosen greedily by evidence overlap, tooth and deterministic-attribute agreement. Free-text attributes are judged by the Grader (`claude-opus-5-5`); `uncertain` counts as wrong. Assertion is scored exactly, and a separate `negation` dimension treats `absent`/`denied` as one class.
- **E3 questions** are scored separately from E2 flags. A false alarm marked *(technical)* is a safeguard flag (failed check, open task), not a clinical rule.
- **"After human review"** is not measured yet: it needs review sessions run by people in the UI.
- **Fault injection** converts gold to graph entities with whole-utterance spans and automatically found derivations. A gold value with no spoken form in its own evidence (e.g. a diagnosis line that doesn't say the tooth) is converted with that value null and listed as a conversion gap.

## Changes made from the dev-v1 results
- **Treatment on a recorded control/adjacent/referred tooth** now fires `treatment_target_mismatch` (high) even when no clinical target was identified. In dev-v1, m02 team mode: Br never identified #14 as the target, so a filling scheduled on control tooth #3 got only a low `target_not_assessable`. The record itself says that tooth isn't the problem tooth, and a relationship never explains treatment (6.2).
- **Cs calibration v2.** dev-v1 fault injection: Cs caught 27/28 association-preserving faults but falsely rejected 25/85 unmodified gold entities (29%). Team mode produced 73 false-alarm flags against the baseline's 11, 64 of them technical safeguards driven by those rejections. The two largest sources were symptom `aspect` labels (onset vs duration, trigger vs biting pain for the same words) and `clinician_observation` vs `test_response`. Now `symptom.aspect` is compared as part of the symptom's free-text description, and those two sources count as equivalent. Patient-vs-clinician attribution stays strict, so the patient-as-clinician fault is still caught.

## Cost controls (after the credit outage)
- **Real-call gate.** `default_client()` and the Deepgram adapter refuse to make real calls unless `SCRIBE_ALLOW_REAL=1` is set. It is set only after the user's explicit "run real". Without it, a pipeline stage fails cleanly (stage-run record and task), as with any other agent error. The Streamlit UI therefore needs `SCRIBE_ALLOW_REAL=1` to process new visits.
- **Ledger.** Every call through a real client (pipeline agents, E3, Grader, fault-injection Cs/Ce, Deepgram) appends one line to `data/api_ledger.jsonl` (model, tokens, estimated USD, result). The Grader's traces now also go to `<results>/grader_traces.jsonl`, and fault injection's to `<results>/fault_traces.jsonl`. Usage before the ledger is reconstructed in `eval/results/api_usage_history.md`.
- **Tests are offline by construction.** `tests/conftest.py` refuses and fails any internet socket connection, swaps `default_client` for the schema-valid `FakeLLM`, and unsets the gate. Before this, tests that edited an entity used by E3 called the real API (E3 re-derives with the default client): 4 billed calls per suite run.
- **Finishing stage 7 without repeating spend.** `run_eval --rescore <dir> --only …` re-grades existing sessions without re-running the pipeline. `run_eval --merge BASE PATCH…` combines a results folder with just the re-run cases, with no model calls. The machinery (pipeline → Grader → report/CSV/review sheet, rescore, merge, fault injection, freeze guard) is tested offline in `tests/test_eval_offline.py`.

## Post-evaluation fixes (after the frozen held-out run; held-out results untouched)
These change frozen files on purpose, so `eval.freeze --check` now lists them; `eval/FROZEN.json` remains the record of the configuration the held-out run used.
- **Tooth numbers and case.** `spoken_tooth_number` and Cv's quote check were already case-insensitive ("Number twelve" reads as 12); a regression test now pins this. The held-out tooth failures that looked like case problems were derivations whose words weren't in any cited span (e.g. a problem citing u2/q2 while "Number twelve" is in u11), or teeth with no derivation at all. Those are correct rejections.
- **Rendering.** Only a `severity` symptom score renders as "/10"; other symptom numbers (e.g. lingering seconds) don't. A prescription or medication dose equal to its strength renders once.
- **Outgrown allergies.** The extraction guide now says an allergy the patient outgrew, or a drug of that class taken since without a reaction, is `reported_resolved`, even when hedged. Not yet verified with a real run.
- **Default mode** is baseline in the UI and in the orchestrator fallback; team stays an option.
- **Staged repair revisions (bug).** Applied repair revisions used to stay in `staging.json` as "staged" and counted as open staged records blocking dentist approval. They are now marked `committed` (or `unchanged`), and a revision that fails validation gets its own task. This inflated the "approval blocked before human review" figure in earlier reports.
- **Scoring additions.** Reports now include tooth accuracy on tooth-bearing item types only, plus a table of every raised flag not matched to gold. For the frozen held-out and final dev results these are in `supplement.md`, recomputed offline from the stored sessions. Matching is deterministic, so the totals reproduce the frozen reports' tooth figures exactly.

## Review page for dental assistants
- **Plain language first.** The review page shows no internal ids or check vocabulary. `pipeline/plain.py` words entities, check failures ("a second read says tooth: #14 (the note says #15)"), conflicts ("Blood pressure doesn't match the quick note (128/84 said vs 162/98 written)"), tasks and staged records. Ids, rule ids, raw check results and JSON stay in collapsed "Details" sections and on the Technical log page.
- **Checklist.** `approval.blocker_items()` returns the approval-matrix blockers as structured items (`blockers()` still returns the same strings). The page groups them by entity, so a failed check and its review tasks are one line, with one-click actions: Looks right / Confirm, Edit, Send to dentist, Not discussed / I reviewed it, Keep one / Both are right, Accept / Reject, Discard, Done. Actions with a reason use the page's optional note, or "Reviewed by the <role> against the transcript".
- **Settling an entity settles its tasks.** Confirming, editing or removing an entity also completes the open `check_failure` / `registry_issue` / `human_override_check` tasks about it. Each gets its own `task_completed` disposition bound to the task's inputs hash, so the approval matrix is unchanged.
- **Navigation.** Pages are switched by a radio, not tabs, so Process can select the new visit and open Review. The visit list is newest first, labeled case · visit date · processing time · mode.
- **Note text** no longer shows the linked option's id after a decision.
- **Each issue once.** The checklist reports what it covers: flags, entities, tasks, conflicts and its own wording. "Other alerts" then skips any flag already on the checklist, any safeguard flag that only restates a checklist item (a failed check, an open task, a conflict), and any alert with the same wording as a checklist line. The remaining alerts are merged by wording, shown once under the highest severity, with actions applying to every merged flag.
- **BP wording.** The alert names only the readings at or over the Level A/B thresholds, where each came from ("from the quick note" / "said in the visit") and "not confirmed" when the reading isn't accepted. The flag's stored message still lists every reading, as 9.2 requires.
- **Second-read wording** quotes what differs ("a second read described the diagnosis as '…' (the note says '…')"), parsing the quoted values directly so values containing "; " survive. Internal values are shown in words ("the patient", "in the past").
- **Phantom staged records** from sessions processed before the staging fix (an applied revision: existing entity id, converted entity, no errors, still "staged") are not open records. They are hidden from the page and don't block approval; the stored file is unchanged.
- **Sign-off** shows only the step that applies (assistant: "Mark my review complete" while in draft; dentist: "Approve the note" after the assistant's review, "Export" after approval), plus who approved or exported and when. "Refresh clinical review questions" is offered only before approval.
- **Visit list** labels are "case · Mon DD HH:MM · mode", short enough for the sidebar, with the full details (processed time, mode, visit date, dentist) in a caption under the list.

## Review cards (choose, then save once)
- **Cards.** Each blocking item is a card: a short title and a tag (e.g. Tooth, Medicine, Timing, Disagreement, Wording), two side-by-side boxes ("Note says" / "Quick note says" / "First said" against "Said in the visit" / "Then said", with the exact quote and who said it), and one choice group. Built by `plain.build_cards()` from the grouped approval blockers; each choice maps to the actions it takes.
- **Choice group.** `st.segmented_control` (single selection) is the choice group. It holds the selection on the page, moving the selection is a click, and "Ask dentist" is one of its options. CSS on the selected button (`button[data-selected]` inside `stButtonGroup`) turns it green, a "✓ " prefix marks it, and labels don't wrap. No custom component was needed. Choice keys are per role, because the assistant's and the dentist's options differ.
- **Save once.** "N of M answered" and one "Save my review" button (disabled with "Answer every item first" until every card has a choice). `human.apply_review()` runs every choice through the same action functions on one shared working graph and commits once: one new graph version, one rebuild. "Ask dentist" marks are applied first; buffered assertion and staging writes happen only after the commit succeeds.
- **Wording-only items** (the second read failed while the quote and value checks passed, and nothing changed to a tooth, drug, dose, number, negation, decision, diagnosis, allergy status, timing, speaker or complaint link) are folded under "N more items look right · show", pre-set to "Looks right" (for an assistant on a critical type, which they can't pass, pre-set to "Ask dentist").
- **No "second read" sentences on the page.** The card shows the note and the quote side by side; the raw check results stay in each card's collapsed Details.
- **Visit list.** A scrollable radio list replaces the dropdown, so options wrap instead of truncating: the case name on line 1 and "Mon DD HH:MM · mode" as its caption on line 2. The sidebar is slightly wider (330 px). The list's help icon shows the selected visit's full details (processed time, mode, visit date, dentist); Streamlit has no per-option hover text, and these options don't truncate.
- **Start page.** The Dentist field defaults to blank.
- **Administrative remarks** (costs, estimates, insurance, billing, paperwork, who to call about scheduling) are excluded by the extraction guide; an `instruction` is a clinical or home-care direction to the patient. This is a prompt change, not yet verified with a real run.

## Assistant workflow (Kirstin)
- **Wrong visit opened (bug).** The visit list was one radio; a click was matched back to a visit by position/label, so two visits with the same name or a list that changed between runs could open another visit. Each visit is now its own button keyed by the session id, and the page heading is "Patient · visit date · Dentist" so a mismatch would be visible. `tests/test_app_flow.py::test_clicking_a_visit_always_opens_that_visit` covers duplicate names and a shifting list.
- **Patient name.** "Patient (name or chart #)" is required and stored in the session's `session.json` (`patient`), not in `VisitMeta`, because `schemas/` is frozen. It is the visit name everywhere. Sessions started from a test case carry `test: true`; they and older case-only sessions are hidden from the visit list unless switched on in Admin.
- **Tabs.** `st.tabs(key="page", on_change="rerun")` is state-controlled in this Streamlit version, so real tabs replace the radio and an action can still open a tab. Only the open tab's page runs.
- **Speaker roles** for a new recording are asked on the Review page itself ("Who is speaking?") because the assistant can't continue without them; the same form sits in Admin for changing roles later.
- **Messages.** `notify(slot, …)` / `show_notice(slot)` put each confirmation or error beside the button that caused it. `plain.friendly_error()` turns any exception into one plain sentence; the raw text is kept only as "Last error (technical)" in Admin.
- **Sign-off.** One primary button at a time: "Save my answers" while cards are open, then "Send to the dentist" (assistant) or "Approve the note" (dentist). Once approved, the checklist, alerts, editing and "Add something" are hidden.
- **Card comments.** Each card has its own optional comment, used as the reason for that card's actions (`apply_review` takes a per-choice `reason`). A comment typed with "Ask dentist" is shown on the dentist's card.
- **Chart-style note.** `pipeline/chart.py` words the same graph as a chart note for the page and the exports. `pipeline/render.py` (the hashed, graded E0 note that approval binds to) is unchanged, so no evaluation output or approval hash moves. An other-tooth relation of "unknown" is not written into the chart line; the tooth-check alert covers it.

## Extraction additions without touching frozen files
- The frozen guide tells extractors to "put the hedge in `reaction`", which is how "I think" became an allergy reaction on the new case8 run, and it never mentions `result_description`, so a described test result (a bite-paper mark) could be dropped. Both are corrected in `agents/extract_common.py::EXTRACTION_ADDENDUM`, appended to the system prompt after the guide. `prompts/` and `eval/FROZEN.json` are unchanged, and `eval.freeze --check` lists the same three files as before. Because the addendum is outside the frozen set, the frozen hash does not record it: a new evaluation run would use it, and should be reported as a new configuration. Not yet verified with a real run.
- `pipeline/linker.py::clean_attributes` also clears an allergy `reaction` that is only a hedge or a "none stated" placeholder, whatever the model returns.

## Exports, worklists, downloads and playback
- **Exports.** `pipeline/exports.py` builds the approved chart note as PDF (fpdf2, default button), Word (python-docx) and plain text ("Copy as text", a small v2 component that writes to the clipboard). Markdown is not offered on the page; `approval.export` (the .md audit export with flags and overrides) is unchanged but no longer has a button. Every note export re-checks the approval binding and refuses a note that changed after approval. A download does not move the session to `exported`; "approved" is the final state the assistant sees.
- **PDF fonts.** The built-in PDF fonts cover Latin-1 only. Common punctuation is mapped and other accented letters fall back to their base letter (Nguyễn → Nguyen) rather than failing. Bundling a Unicode font would remove this limit.
- **Worklists.** "Waiting for dentist" lists sessions in `assistant_review_complete` (longest wait first, from the assistant's sign-off time); "Cleared by dentist" lists approved sessions, newest approval first, with PDF / Word / Everything buttons whose files are built only when clicked.
- **Recording format.** The recording downloads in its original format. No audio converter (ffmpeg) is installed, so there is no mp3 re-encode.
- **Bundle.** "Download everything" is a zip containing one folder "<Patient> <date>" with note.pdf, note.docx, transcript.txt, transcript.pdf and the recording. It needs an approved note; the transcript and recording buttons work at any stage.
- **Timestamps and player.** For a visit with a recording, each transcript line starts with its time as a link to `#t=<seconds>`, and a quoted line on a review card is the same kind of link (matched to the first utterance containing the quote). `components.audio_player` renders an ordinary `st.audio` and a script that pins a bar to the bottom of the window driving that element (play/pause, scrub, current time, ±10 s), handles the `#t=` links, and marks the line being spoken. If the script can't run, the ordinary player stays visible. Pasted transcripts have no times and no recording, so neither appears.
- **Not verified with a real recording.** Record/upload → Deepgram → "Who is speaking?" was not run end to end here (no real calls). The player, timestamps and downloads were checked in a browser against an offline session with a generated tone and times written onto the test transcript.

## Review hand-off and cards (tested against a "Bear"-shaped visit, `tests/bear.py`)
- **One bar, one button.** A bar fixed to the bottom of Review shows "N of M answered" and a single button: "Send to the dentist" (assistant) or "Approve the note" (dentist) saves every answer and hands the note on in one click; "Save my answers" appears only when the role can answer but not hand on. `position: sticky` did not hold inside the tab panel, so the bar is `position: fixed` across the window with its contents at the right (the sidebar draws over its left end).
- **Dentist approves after their own fixes.** Any change still returns a note to draft, but `approve_dentist(after_own_changes=True)` lets the dentist approve in the same click as their own answers when the note had been sent by the assistant. The dentist's approval checks are a superset of the assistant's, and the approval record binds the changed note. Without this, every dentist fix bounced the note back to the assistant.
- **"Ask dentist" for the assistant.** What she passed on is listed in one collapsed "Sent to the dentist ✓" group, built from the same cards the dentist will answer; no alert icons or Dismiss buttons. The dentist's cards are marked "<assistant> asked about this" (name from the visit's Assistant field) with her comment, and come first.
- **Fixes on safety cards.** Allergy vs prescription: Remove prescription / Change prescription (the editor opens inside the card and is saved with the other answers; review op `edit`) / Prescribe anyway (reason required, recorded as the dentist's dismissal). Tooth: "Use tooth #N" (review op `use_tooth`) sets the problem tooth and the tooth of every item on the card and of the problem's treatment-type items that named another candidate tooth; a conflict between two items of the same type keeps the one on the chosen tooth, any other conflict is closed as "both kept" with the choice as the explanation. Blood pressure: Use X / Use Y / Both are right, with the high-reading alert shown on that card. "Reviewed, OK" stays only on informational alerts.
- **Settle step.** After the save, alerts that the dentist's choice answers (the tooth rules for that problem, `bp_reading`) are recorded as dismissed by the dentist with the choice as the reason, and unmatched statements about the same teeth are completed. Otherwise the same question returned as a new card after the rebuild. A finding on the other tooth is not moved by "Use tooth #N"; only treatment-type items and the items on the card are.
- **One card per disagreement.** Tooth alerts (`treatment_target_mismatch`, `treatment_target_disagreement`, `quick_note_target_conflict`), conflicts whose participants or quotes name different teeth, and unmatched contradictions about teeth are one "Which tooth is it" card. A failed check on an item that is part of a disagreement is answered on the disagreement's card (choosing a side confirms the kept item where the role may). A resolution that removes an item also completes that item's open check task.
- **Button labels name values** ("Tooth #2", "No allergies", "Penicillin allergy (hives)", "Use 132/84"); when both sides read the same, the source is added. Card titles have Markdown markers removed and are never cut short.
- **Quick-note labels.** A treatment-type item whose only evidence is a quick-note line of the form "Tx:/Tooth:/Dx: <tooth>" is not created (`linker.label_only_quick_note`); the output stays in staging with status `label_only`, and the tooth rules still read the quick note. The extraction addendum says the same. "Allergy: none" / "NKDA" wording is treated as no substance: "No known allergies", shown with "(quick note)" on cards and on the Review note line (not in the exported note).
- **Not verified with real calls.** The addendum changes and the Bear visit itself were not re-run; the fixture reproduces the reported situation with a fake model client.
